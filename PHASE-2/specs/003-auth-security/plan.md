# Implementation Plan: Todo Full-Stack Web Application – Authentication & Security

**Branch**: `003-auth-security` | **Date**: 2026-02-10 | **Spec**: [spec.md](spec.md)
**Input**: Feature specification from `/specs/003-auth-security/spec.md`

## Summary

Implement secure, stateless authentication using Better Auth (JWT plugin
with EdDSA/Ed25519) on the Next.js frontend and JWKS-based JWT
verification on the FastAPI backend. Every API endpoint requires a valid
JWT; user identity is derived exclusively from the token `sub` claim.
User isolation is enforced by validating the URL `user_id` parameter
against the JWT identity on every route.

**Current state**: The authentication system is **already implemented**
across both frontend (`frontend/lib/auth.ts`, `frontend/lib/auth-client.ts`,
`frontend/lib/api.ts`) and backend (`backend/src/dependencies.py`,
`backend/src/api/tasks.py`). This plan documents the architecture,
verifies completeness against the spec, and identifies any remaining gaps.

## Auth Architecture

### Token Lifecycle

```text
1. User signs up/in → Better Auth creates session + issues JWT
2. Frontend calls authClient.token() → receives EdDSA JWT
3. Frontend api.ts attaches: Authorization: Bearer <jwt>
4. Backend verify_jwt dependency:
   a. Extracts token from Authorization header
   b. Fetches public key from JWKS endpoint (cached)
   c. Verifies signature (EdDSA/Ed25519)
   d. Checks expiration
   e. Returns payload with sub=user_id
5. Route handler calls _verify_user_id(url_user_id, payload)
   a. Compares str(url_user_id) == payload["sub"]
   b. 403 if mismatch
6. Business logic executes with verified user_id
```

### Key Design Decisions

| Decision | Choice | Rationale |
|----------|--------|-----------|
| Token signing | EdDSA (Ed25519) | Fastest verification, smallest key size, modern |
| Key exchange | JWKS endpoint | Asymmetric — backend never needs signing secret |
| Backend secret | None (JWKS only) | Backend only verifies; no need for shared secret |
| User identity | JWT `sub` claim | Standard claim, universally supported |
| Session storage | Better Auth managed | Frontend delegates to library; backend is stateless |
| Authorization | Per-route check | `_verify_user_id()` called in every route handler |

### Security Boundaries

| Boundary | Enforcement |
|----------|------------|
| Unauthenticated → Protected | `HTTPBearer` + `verify_jwt` → 401 |
| Cross-user access | `_verify_user_id()` → 403 |
| Expired token | `jwt.ExpiredSignatureError` → 401 |
| Tampered token | `jwt.InvalidTokenError` → 401 |
| Wrong secret/key | JWKS key mismatch → 401 |
| Frontend route | `useSession()` + redirect to `/signin` |

### Identified Gap: FR-011

**Issue**: When the backend returns 401 (expired/invalid token), the
frontend `api.ts` throws an `ApiError` but does not redirect to
`/signin`. The user sees a generic error instead of being redirected.

**Fix**: Add 401 detection in `apiFetch()` that triggers a redirect to
`/signin` (or calls `signOut()`) when the backend rejects a token.
