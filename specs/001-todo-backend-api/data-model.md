# Data Model: Todo Full-Stack Web Application

**Feature Branch**: `001-todo-backend-api`
**Date**: 2026-02-09

## Entities

### User (managed by Better Auth)

Better Auth creates and manages the `user` table. The FastAPI
backend reads from this table but does not write to it.

| Field        | Type         | Constraints                          |
|--------------|--------------|--------------------------------------|
| id           | UUID (PK)    | Generated by Better Auth             |
| email        | VARCHAR(255) | UNIQUE, NOT NULL                     |
| name         | VARCHAR(255) | NULLABLE                             |
| image        | TEXT         | NULLABLE (avatar URL)                |
| created_at   | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()              |
| updated_at   | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()              |

**Note**: Better Auth also creates `session`, `account`,
`verification_token`, and `jwks` tables. These are managed
entirely by Better Auth and are not modeled in SQLModel.

### Task (managed by FastAPI / SQLModel)

| Field        | Type         | Constraints                          |
|--------------|--------------|--------------------------------------|
| id           | UUID (PK)    | DEFAULT uuid4(), NOT NULL            |
| user_id      | UUID (FK)    | REFERENCES user(id), NOT NULL, INDEX |
| title        | VARCHAR(500) | NOT NULL, min_length=1               |
| description  | TEXT         | NULLABLE, DEFAULT NULL               |
| is_completed | BOOLEAN      | NOT NULL, DEFAULT FALSE              |
| completed_at | TIMESTAMPTZ  | NULLABLE, DEFAULT NULL               |
| created_at   | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW()              |
| updated_at   | TIMESTAMPTZ  | NOT NULL, DEFAULT NOW(), ON UPDATE    |

**Indexes**:
- `ix_task_user_id` on `user_id` (query all tasks for a user)
- `ix_task_user_id_is_completed` on `(user_id, is_completed)`
  (future: filter completed/incomplete tasks)

## Relationships

```text
User (1) ──── (0..*) Task
  │                      │
  └─ id (PK)            └─ user_id (FK → user.id)
```

- One User has zero or more Tasks.
- Each Task belongs to exactly one User.
- Deleting a User cascades to delete all their Tasks.

## Validation Rules

### Task Creation (`POST`)
- `title`: required, string, 1–500 characters
- `description`: optional, string, no max length enforced

### Task Update (`PUT`)
- `title`: required, string, 1–500 characters
- `description`: optional, string

### Task Complete (`PATCH`)
- No request body required (idempotent toggle to `true`)

## State Transitions

```text
Task States:
  [Created] ──PATCH /complete──→ [Completed]
      │                               │
      └──── PUT (update) ────┘       │
      └──── DELETE ──→ [Deleted]     │
                                      └──── DELETE ──→ [Deleted]
```

- Tasks are created with `is_completed = false`.
- `PATCH /complete` sets `is_completed = true` and
  `completed_at = NOW()`.
- Completing an already-completed task is a no-op (idempotent).
- There is no "uncomplete" operation in the current spec.
- `DELETE` permanently removes the task (hard delete).
